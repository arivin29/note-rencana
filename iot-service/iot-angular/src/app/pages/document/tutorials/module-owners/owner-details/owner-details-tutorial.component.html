Apa itu Owner Detail View?

Owner Detail View adalah halaman dashboard management lengkap untuk satu owner/company specific, menampilkan snapshot statistics, user management (CRUD users), dan data forwarding configuration (Webhook, MySQL, PostgreSQL).

Multi-Function Dashboard

Owner Detail View combines 3 major functions:

  • Statistics Snapshot: Quick view projects, nodes, sensors count untuk owner ini
  • User Management: Full CRUD untuk users yang belong to owner (add, view, toggle status, delete)
  • Data Forwarding: Configure real-time data delivery ke external systems (Webhook/MySQL/PostgreSQL)
Kenapa Penting?
  • Centralized Management: All owner-related settings dalam satu dashboard
  • User Access Control: Manage users yang bisa access owner's projects & nodes
  • Data Integration: Forward telemetry data ke external command centers, data warehouses, atau analytics platforms
  • Real-time Delivery: Webhook push data immediately, Database batch insert untuk bulk processing
  • Multi-tenant Ready: Each owner independent, isolated data forwarding configurations

Cara Akses Owner Detail View

Ada beberapa cara untuk mengakses Owner Detail View:

Via Owner List (Most Common)
  1. Buka IoT → Owners menu
  2. Klik pada baris owner (anywhere) atau tombol View Detail (eye icon)
  3. Owner detail dashboard akan terbuka
Via Dashboard Widget
  1. Dari Main Dashboard, klik owner name di widget
  2. Direct link ke owner detail view
Via Direct URL

Akses langsung via browser (if you know owner UUID):

https://your-domain.com/iot/owners/{{ '{' }}ownerUUID{{ '}' }}

Cara Menggunakan

Melihat Owner Information
  1. Buka owner detail page (via owner list atau dashboard)
  2. Check Owner Snapshot card untuk quick stats:
    • Contact person details
    • Projects, Nodes, Sensors count
    • Forwarding health status
  3. Scroll down untuk see Users table (semua users yang belong to owner)
  4. If needed, edit owner basic info via Edit Owner button

Dashboard auto-loads fresh data dari backend on page load

Menambah User Baru
  1. Scroll ke Users section
  2. Klik tombol "+ Add User"
  3. Modal form akan muncul
  4. Isi form user:
    • Full Name: Nama lengkap user
    • Email: Email untuk login (must be unique)
    • Password: Initial password (min 8 characters)
    • Role: Admin/Manager/Viewer (dropdown)
    • Owner: Auto-filled (current owner, read-only)
    • Status: Active/Inactive checkbox
  5. Klik Save
  6. Modal close, users table auto-reload dengan user baru

Result: User baru muncul di table, bisa langsung login dengan email & password

View User Detail
  1. Di users table, klik tombol View (eye icon) pada user
  2. System akan navigate ke User Detail Page (module Admin → Users)
  3. Di user detail page, bisa:
    • View complete user profile
    • Edit user information
    • Change password
    • View login history
    • Manage permissions

User detail page ada di Admin module, bukan di Owner module

Toggle User Status (Activate/Deactivate)
  1. Di users table, klik tombol Toggle Status (power icon)
  2. Confirmation dialog akan muncul:
    • If user Active → "Are you sure want to deactivate user?"
    • If user Inactive → "Are you sure want to activate user?"
  3. Klik OK untuk confirm
  4. Status badge di table akan berubah:
    • Active → Inactive (green badge → gray badge)
    • Inactive → Active (gray badge → green badge)

Effect: Inactive users cannot login - existing sessions akan terminated

Delete User
  1. Di users table, klik tombol Delete (trash icon merah)
  2. Confirmation dialog shows:
    • User name & email
    • Warning: "This action cannot be undone"
  3. Klik OK untuk confirm delete
  4. User removed dari table immediately

Data Loss Warning: User account, login history, dan audit logs akan permanently deleted

Configure Webhook Forwarding

Setup real-time data push ke external webhook:

  1. Klik tab Webhook di Data Forwarding card
  2. Toggle Enable switch ON
  3. Fill webhook configuration:
    • Label: Descriptive name (e.g., "Command Center Webhook")
    • Endpoint URL: Target webhook URL (https://hooks.example.com/iot/ingest)
    • HTTP Method: POST atau PUT
    • Secret Token: Authentication token (optional)
    • Payload Format: Timeseries (envelope) atau Raw (direct)
    • Max Retry: Berapa kali retry jika delivery failed (default 3)
    • Backoff Ms: Delay between retries dalam miliseconds (default 2000)
  4. Custom Headers (optional):
    • Klik "Add Header"
    • Enter key-value pairs (e.g., X-Tenant-Code: ADHI-WATER)
    • Repeat untuk multiple headers
  5. Klik Save Configuration
  6. Klik Test Delivery untuk verify webhook works
  7. Check test result message - should show success & duration

Result: Telemetry data dari owner's nodes akan automatically pushed ke webhook endpoint real-time

Configure MySQL Database Forwarding

Setup batch data insert ke MySQL warehouse:

  1. Klik tab MySQL di Data Forwarding card
  2. Toggle Enable switch ON
  3. Fill database connection details:
    • Label: Descriptive name (e.g., "MySQL Warehouse")
    • Host: MySQL server address (e.g., mysql-fw.company.local)
    • Port: MySQL port (default 3306)
    • Database: Database name (e.g., iot_forwarder)
    • Username: DB username dengan INSERT permission
    • Password: DB password (encrypted in backend)
    • Target Table: Table untuk insert data (e.g., telemetry_logs)
    • Write Mode: Append (always insert) atau Upsert (update if exists)
    • Batch Size: Berapa rows per batch insert (default 200)
  4. Klik Save Configuration
  5. Klik Test Connection untuk verify database accessible
  6. Check test result - should show connection success & duration

Data inserted in batches (not real-time) - efficient untuk large volume telemetry

Configure PostgreSQL Database Forwarding

Setup sama seperti MySQL, dengan additions:

  1. Klik tab PostgreSQL
  2. Toggle Enable & fill connection details (sama seperti MySQL)
  3. Additional PostgreSQL-specific field:
    • Schema: PostgreSQL schema (default "public")
  4. Port default PostgreSQL: 5432 (bukan 3306)
  5. Save & Test Connection

Bisa enable both MySQL & PostgreSQL simultaneously - data akan forwarded ke both

Memahami Data Forwarding

Webhook vs Database Forwarding
Aspect Webhook Database (MySQL/PostgreSQL)
Delivery Real-time push (immediate) Batch insert (periodic)
Use Case Command centers, dashboards, alerts Data warehouses, analytics, reporting
Protocol HTTP POST/PUT SQL INSERT/UPSERT
Data Volume Low to medium (per telemetry event) High (bulk batches)
Retry Logic Configurable (max retry + backoff) Built-in batch retry
Security Secret token, custom headers DB credentials, SSL connection
Webhook Payload Formats

1. Timeseries Envelope (Recommended):

{{ '{' }}
  "owner": "ADHI-WATER",
  "timestamp": "2025-12-24T09:15:00Z",
  "data": [
    {{ '{' }}
      "node": "ESP-CS-F03",
      "sensor": "SENSOR-PM-01",
      "channel": "voltage_l1",
      "value": 230.5,
      "unit": "V"
    {{ '}' }},
    {{ '{' }}
      "node": "ESP-CS-F03",
      "sensor": "SENSOR-PM-01",
      "channel": "current_l1",
      "value": 15.2,
      "unit": "A"
    {{ '}' }}
  ]
{{ '}' }}

2. Raw Channel Payload:

{{ '{' }}
  "voltage_l1": 230.5,
  "current_l1": 15.2,
  "power_l1": 3500,
  "energy_total": 12500
{{ '}' }}
Database Target Table Schema

Table harus have minimum columns:

  • id - Auto-increment primary key
  • owner_id - UUID owner
  • node_id - UUID node
  • sensor_id - UUID sensor
  • channel_id - UUID channel
  • metric_code - Channel metric name
  • value - Measurement value (DECIMAL)
  • unit - Unit string
  • timestamp - Measurement timestamp (DATETIME/TIMESTAMP)
  • created_at - Insert timestamp

Scenario: Deactivate User yang Resign

Situasi: User "operator" resign dari company, perlu revoke access

Langkah:

  1. Open owner detail view
  2. Scroll ke Users table
  3. Find user "[email protected]"
  4. Klik Toggle Status (power icon)
  5. Confirm deactivation
  6. Status badge changes: Active (green) → Inactive (gray)
  7. User's active sessions akan terminated immediately

Scenario: Troubleshoot Webhook Delivery Failed

Situasi: Webhook forwarding failed, last status shows "Failed"

Langkah:

  1. Open owner detail view
  2. Go to Webhook tab
  3. Check Last Status & Last Error message
  4. Common issues:
    • 403 Forbidden: Check secret token correct
    • 404 Not Found: Verify endpoint URL typo
    • Timeout: Increase retry backoff ms
    • SSL Error: Check certificate valid
  5. Fix configuration based on error
  6. Save changes
  7. Klik Test Delivery
  8. If test succeed, webhook will auto-resume forwarding
  9. Monitor status untuk confirm recovery

System automatically retries failed deliveries based on retry config

Scenario: Migrate dari Webhook ke Database Forwarding

Situasi: Command center overloaded dengan real-time data, switch to batch database insert

Langkah:

  1. Open owner detail view
  2. Setup database forwarding first (MySQL atau PostgreSQL):
    • Configure connection details
    • Set large batch size (500+)
    • Save & test connection
    • Toggle Enable ON
  3. Wait 10-15 minutes untuk verify data flowing ke database
  4. Query database untuk confirm telemetry data inserted correctly
  5. If database working well:
    • Go to Webhook tab
    • Toggle Enable OFF
    • Save configuration
  6. Forwarding status akan change dari "Operational" (webhook) ke "Operational" (database only)
  7. Notify command center team tentang migration

Bisa enable both webhook & database simultaneously untuk hybrid approach

Tips & Best Practices

Common Pitfalls:
  • Duplicate user emails: Email must be unique across entire system - cannot reuse
  • Wrong webhook endpoint: Typo in URL will cause all deliveries to fail
  • Missing secret token: If target requires auth, delivery will fail 401/403
  • Database credentials wrong: Test connection before enable - avoid failed batches
  • Too small batch size: Batch size 10 untuk high-volume telemetry = slow & inefficient
  • No retry configured: Network hiccup akan cause data loss if max retry = 0
Pro Tips:
  • User roles: Admin untuk owner admin, Manager untuk supervisors, Viewer untuk read-only users
  • Webhook testing: Always test delivery before enable - prevent failed queue buildup
  • Custom headers: Use X-Tenant-Code untuk multi-tenant webhook endpoints
  • Payload format: Timeseries untuk structured data, Raw untuk simple key-value
  • Retry tuning: Max retry 3 dengan backoff 2000ms = good default untuk most webhooks
  • Batch size tuning: 200-500 good balance - larger batches save DB connections
  • Write mode: Append untuk time-series data, Upsert untuk state data (latest value)
  • Database schema: Create indexes on owner_id, node_id, timestamp untuk fast queries
  • Monitor forwarding status: Check "Forwarding Health" badge regularly
  • Deactivate vs Delete: Deactivate untuk temporary suspension, Delete untuk permanent removal
